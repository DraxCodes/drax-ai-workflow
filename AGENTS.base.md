## Workflow base

This project uses the vendored workflow base **drax-ai-workflow** v{{version}}. The seam is
`.opencode/workflow.json`; validate it with `node .opencode/tools/base.mjs doctor .`. If the
seam is missing, these workflows are dormant: say so and stop.

`.opencode/agents`, `.opencode/commands`, `.opencode/skills`, `.opencode/packs` and
`.opencode/tools` are generated by the base. Edit the base repo, not those files. Check for
drift with `node .opencode/tools/base.mjs check .`; update with
`... update . --from <base>`; remove with `... eject .`.

`.github/skills` and `.github/agents` are a generated bridge for VS Code Copilot Chat, from
the same source. Never hand-edit them; the canonical files are under `.opencode/`. Copilot
reads this `AGENTS.md` directly, so the rules below apply there unchanged. If `.github/` is
missing, this project was installed with `--no-copilot` and only the OpenCode tree exists.

### Starting a project

A new project starts with `/start-project <idea>`. It writes an approved first spec
in the issue directory and stops before any code; if at least two council triggers
hold it asks for `/council` first.

### Hillclimb

When a task is quality-sensitive — UI, UX, visual, copy or docs — or has a clear,
measurable objective (coverage, warnings, build/test time, bundle size, response time),
or is a decision that may be missing an obligation (a spec, a proposal, a feature), ask
whether to run the hillclimb workflow before implementing it directly. It is opt-in.

The gate is **one named rubric** in the `hillclimb` skill
(`references/rubrics/<name>.md`), plus the project addendum named by the seam.
Selection: an explicit `Rubric: <name>` wins, then the seam's `rubrics.default`, then
`perception`.

| Rubric | Use for |
| --- | --- |
| `perception` | UI, UX, visual surfaces, copy (the default) |
| `usability` | API, CLI, errors, logs, docs |
| `performance` | latency, throughput, size, build time, cost |
| `completeness` | a spec, proposal or feature: what did we not decide? |

- **Below 8:** name the specific flaws holding it back, fix those, and iterate.
- **8 or above:** stop and ship, unless the task explicitly demands a 10.
- **8–9 with a 10 demanded:** name what a 10 requires, attempt at most two iterations, then
  stop and report the ceiling if the score does not move.
- **Floor:** the seam's `checks` (build, test, free) must pass. A red floor cannot score 8.

The score is the only iterate/stop signal. A green floor does not earn a ship; a number
moving does not earn a ship.

### Council

For a larger feature — one where the shape is worth more than the code — run a council
before planning. Convene when at least two of these hold: a new user-facing surface; a new
subsystem, protocol, dependency or transport; it crosses a seam; it is expensive to
reverse; more than one design is credible; or the user asks.

A council is **divergence**: whether to build, what it must feel like at 8/10, and which
trade-off is accepted. Hillclimb is **convergence**: whether the built artifact is good
enough. Security is a veto lens in both; the user decides value.

`/council <proposal>` or the `council` skill. One artifact in the seam's issue directory,
which the spec links. The experience thesis travels into the spec, so the hillclimb gate
scores against intent plus the rubric.

### Working preferences

1. **Pick the approach before coding.** For any non-trivial feature, settle the approach
   with the user before writing code — offer the realistic options with a short trade-off
   each and ask; don't assume.
2. **Verify visual changes with temporary sample data.** Use the seam's seed and capture,
   look at the result, then remove the seed. The project section names the specifics.
3. **Run the free checks, always.** After any code change, run the seam's `checks` and
   report the real output — never a remembered result. Say plainly what was **not run**.
4. **Gate hillclimb on perceived quality, not statistics.** Score with the rubric from real
   evidence. A green number never substitutes for the rubric; tests and build are a floor.

### Spend discipline

Cost follows **context size**, not the number of steps. Three tiers, and they are not
interchangeable:

| Tier | Scope | When |
| --- | --- | --- |
| Lens | one change, as a diff | every change |
| Gate | one artifact, as evidence | every hillclimb iteration |
| Audit | everything since a fixed point | a release or branch end, once |

1. **Scope every review before starting it.** Name the fixed point and the paths, for
   example "the diff from `<tag>` in `tools/` and its tests". "Review the repo" is not a
   scope. If the scope is a whole tree or a very large diff, split it into passes and ask
   first.
2. **Default to the change, not the repository.** A review reads the changed files and
   their tests. Reach for the whole tree only at a release or a tag, and only once.
3. **Give a delegated brief a scope.** A subagent starts with no context: what you paste or
   point it at is the whole cost. Pass paths and a commit range, never "read everything and
   tell me".
4. **Escalate the model, not the scope.** If a finding needs a stronger model, send that
   finding — not the diff it came from. A small model with the right files beats a frontier
   model with the repo.
5. **Say what a big review will cost before running it.** If a task would read more than a
   few hundred files or a multi-megabyte diff, state that in one line and ask.

### Session hygiene

One session per task; `/compact` when switching topics; prefer targeted reads; delegate
isolated work to subagents.

### Conventions

Small atomic commits with a clear scope; never commit secrets or personal data; check
`git status` before committing.

### Where things are

- Seam, precedence, update/eject, issue tracker, domain docs: the `workflow-base` skill.
- Rubric: the `hillclimb` skill.
- Security lens: the `security-auditor` subagent, on every change.
